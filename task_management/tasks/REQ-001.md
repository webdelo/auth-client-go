## Контекст

`webdelo/auth-client-go` — это Go SDK для микросервиса аутентификации `webdelo/auth`. Цель — дать consumer-сервисам (BFF, simple-trader, arbitrage-trader, в будущем другим бэкам) один импорт, после которого правильная работа с AUTH «получается сама собой», без необходимости разбираться в нюансах протокола.

Ключевая идея: тонкая обёртка над сгенерированными gRPC stubs из `github.com/webdelo/auth-proto/go`, но **с правильными решениями**, зашитыми внутрь:

- TTL-кэш ValidateToken (30s по умолчанию) — иначе AUTH захлёбывается
- fail-closed при недоступности AUTH (но опционально fail-open)
- singleflight на refresh — параллельные refresh от одного user_id не валят family detection
- typed errors вместо grpc codes — consumer не ветвится на `codes.Unauthenticated`
- fingerprint binding — SDK вынуждает прокидывать IP/UA пользователя, а не BFF
- стандартные cookie params для refresh — без шанса ошибиться
- Никаких побочных зависимостей (DI, конкретный логгер, метрики) — только adapter-интерфейсы

Текущее состояние репо: scratch lib bootstrap, добавлена AUTH-style infra (`task_management/`, `.claude/`, `.memory_bank/`). Пусто в `lib/` кроме placeholder файлов.

## WHY

1. **Снизить связность consumer-кода и AUTH.** BFF не должен знать про token_version, fingerprint, family rotation, dummy hashing, rate-limit headers, refresh race. SDK инкапсулирует.

2. **Защита от типовых ошибок интеграции.** При написании middleware с нуля легко сделать:
   - бесконечный кэш ValidateToken (заблокированный user продолжает ходить часами)
   - fail-open при недоступности AUTH (auth bypass)
   - забыть про fingerprint и связать refresh с IP BFF
   - неправильные cookie-params (HttpOnly без Secure, SameSite=Lax)
   - игнор Retry-After на 429

3. **Унификация интеграции.** Все Go-сервисы платформы используют один SDK → один API, одно поведение, один changelog. Регрессы ловятся централизованно.

4. **Готовность к multi-language.** Аналогичный PHP SDK (REQ-XXX, отложен) повторит эту же поверхность — фронт-фейсингу Laravel будет очевидно, что делать.

## WHAT — высокоуровнево

### Публичная поверхность SDK (`lib/`)

```go
// === Конструктор и опции ===
client, err := authclient.New(authclient.Config{
    Endpoint:         "auth:50051",
    ValidateCacheTTL: 30 * time.Second,
    FailMode:         authclient.FailClosed,
    Logger:           myLoggerAdapter,
})
defer client.Close()

// === Защита эндпоинтов ===
mux.Handle("/api/secure", client.HTTPMiddleware(handler))
grpcServer := grpc.NewServer(
    grpc.UnaryInterceptor(client.UnaryInterceptor()),
)

// === Доступ к юзеру в handler ===
user := authclient.UserFromContext(r.Context())  // {UUID, Role}
if user.IsAdmin() { ... }

// === Auth flow (для фронт-фейсинг сервисов) ===
tokens, err := client.Login(ctx, authclient.LoginInput{
    Email:     email,
    Password:  password,
    ClientIP:  authclient.IPFromRequest(r),
    UserAgent: r.UserAgent(),
})

tokens, err := client.Refresh(ctx, refreshToken, ip, ua)
err := client.Logout(ctx, refreshToken)
err := client.LogoutAll(ctx, accessToken)
err := client.ChangePassword(ctx, accessToken, current, new)
user, err := client.GetCurrentUser(ctx, accessToken)

// === Cookie-хелперы ===
authclient.SetRefreshCookie(w, tokens.RefreshToken)  // правильные params автоматически
authclient.ClearRefreshCookie(w)

// === Типизированные ошибки ===
if errors.Is(err, authclient.ErrInvalidToken)  { ... }
if errors.Is(err, authclient.ErrExpired)       { ... }
if errors.Is(err, authclient.ErrBlocked)       { ... }
if errors.Is(err, authclient.ErrRateLimited)   { ra := authclient.RetryAfter(err); ... }
if errors.Is(err, authclient.ErrUnavailable)   { ... }
```

## Архитектурные решения

### A1. ValidateToken cache

**Кэш по полному access_token** (а не по `(jti, token_version)`, потому что JWT-парсинг на стороне SDK = лишняя работа и риск рассинхрона валидации). Ключ — sha256(access_token), значение — `(user, expires_at, cached_at)`. TTL 30 секунд по умолчанию.

**Инвалидация:** только по TTL. Когда AUTH инкрементирует `token_version` (смена пароля, LogoutAll, BlockUser), все access tokens, изданные до инкремента, начнут возвращать `is_valid=false` — кэш SDK подхватит при следующем lookup'е после истечения TTL. Худший случай — 30 секунд жизни старого токена в кэше после server-side invalidation. Это приемлемо.

**Что НЕ делаем:** не подписываемся на push-уведомления от AUTH (overengineering для v0.1.0), не парсим JWT (см. выше).

### A2. Fail-mode

`FailClosed` (default): при `ErrUnavailable` (grpc error, timeout, network) middleware возвращает 503. Безопасно.

`FailOpen`: пропускает запрос, в context кладёт пустой `User`. Использовать только для не-критичных эндпоинтов (например, health checks под аутентификацией).

Конфигурируется через `Config.FailMode` либо через `WithFailMode(FailOpen)` функциональную опцию (если решим в этом стиле).

### A3. Singleflight для refresh

Когда у пользователя открыты две вкладки, обе могут параллельно отправить refresh с одним и тем же refresh_token. Если SDK / BFF просто проксирует оба запроса в AUTH — AUTH детектит reuse и убивает family. Пользователь выкидывается.

Решение: `golang.org/x/sync/singleflight.Group` по ключу `sha256(refresh_token)`. Первый запрос идёт в AUTH, второй ждёт и получает тот же результат. AUTH видит ровно один refresh-вызов.

Это работает в пределах одного процесса SDK. Если consumer запускает несколько инстансов BFF — singleflight не помогает (нужен distributed lock, что overkill). Это accepted limitation для v0.1.0, фиксируется в README.

### A4. Логгер и метрики через adapter

```go
type Logger interface {
    Info(ctx context.Context, msg string, fields ...any)
    Warn(ctx context.Context, msg string, fields ...any)
    Error(ctx context.Context, msg string, err error, fields ...any)
}
```

`Config.Logger` принимает реализацию. Дефолт — no-op logger (silent). Consumer передаёт свой адаптер (например, врапер над `webdelo/go-ctx-logger`, но SDK об этом не знает).

Метрики — аналогично, через `Metrics` interface (counter/histogram), no-op по умолчанию. **В v0.1.0 — опционально**, не блокер если отложим до v0.2.0.

### A5. gRPC connection management

Один `*grpc.ClientConn` на `*authclient.Client`. SDK не делает connection pooling — gRPC сам мультиплексирует по HTTP/2. Опция `DialOptions []grpc.DialOption` для consumer'а (TLS, retry policy, keepalive).

`client.Close()` обязателен — закрывает соединение. Это в README/godoc должно быть явно.

## Уточнения

**В1**: Почему SDK не парсит JWT, чтобы валидировать его локально?
**О1**: Локальная JWT-валидация требует знать публичный ключ AUTH и обновлять его при ротации (REQ-001 SEC-10). Это добавляет state в SDK, риск рассинхрона ключей, и не даёт ничего сверх ValidateToken-кэша. Решено: всегда ходить в AUTH (с кэшем).

**В2**: TTL кэша 30 секунд — почему не больше?
**О2**: Это окно, в течение которого заблокированный/разлогиненный admin'ом пользователь продолжает иметь access. Меньше — больше нагрузка на AUTH (каждый запрос = grpc-call). 30 секунд — баланс. Можно настроить через `Config.ValidateCacheTTL`, но min/max ограничить (например `[5s, 5m]`).

**В3**: Почему singleflight только в SDK, а не в AUTH?
**О3**: AUTH — stateless относительно SDK-инстансов. Если делать в AUTH через distributed lock на Postgres — добавляется latency на каждый refresh. SDK-side singleflight снимает 80% реальных race'ов (один SDK-инстанс на BFF). Distributed-кейс — accepted limitation для v0.1.0.

**В4**: А если consumer хочет свой кэш (Redis, кластерный)?
**О4**: В v0.1.0 — встроенный in-memory кэш с интерфейсом `Cache`, consumer может передать свою реализацию через `Config.Cache`. По умолчанию — `internal/cache.MemoryCache`. Distributed-кэш — реализация consumer'а.

**В5**: Что с TLS до AUTH?
**О5**: Через `Config.DialOptions []grpc.DialOption`. По умолчанию в SDK — `grpc.WithTransportCredentials(insecure.NewCredentials())` для dev. Production — consumer передаёт `grpc.WithTransportCredentials(credentials.NewTLS(...))`. README про это явно говорит.

**В6**: Как обновлять `auth-proto` версию?
**О6**: `go get github.com/webdelo/auth-proto/go@<new-tag>` → `go mod tidy` → пересборка SDK → новый тег SDK. CI auth-proto тэгает → ручной/триггер-update в auth-client-go.

**В7**: scratch.yaml оставляем в репо?
**О7**: Да, оставляем. Он маркер для будущих `scratch update-makefile`, `scratch init-mem-bank`. Хотя для lib его использование ограничено.

**В8**: А что с CI? Сейчас в `.github/workflows/ci.yaml` базовый.
**О8**: CI должен в TASK-001 расширить: добавить шаг integration-тестов (через docker-compose с AUTH). Это требует, чтобы CI-runner имел доступ к docker и мог собрать AUTH из исходников или взять опубликованный image (если есть). **Caveat:** docker AUTH-image сейчас не публикуется. Может быть TASK на DevOps в auth-репо (отдельно). Для SDK v0.1.0 — integration-тесты опциональные в CI, обязательные локально.

## Риски и нюансы

### Риск 1 — версия grpc/protobuf не совпала с auth-proto
SDK импортирует `github.com/webdelo/auth-proto/go`, который тянет grpc/protobuf транзитивно. Если в SDK `go.mod` явно фиксирована другая версия (через `replace` или явное `require`) — будут warnings/incompatibility. **Митигация:** не пинить grpc/protobuf вручную, давать MVS выбрать максимум из auth-proto + consumer (в transitivе пройдёт корректно).

### Риск 2 — fingerprint в production
Fingerprint AUTH считается как `SHA-256(UserAgent + first 3 octets of IP)`. Это значит refresh, выданный пользователю на IP `203.0.113.55`, не сработает на `203.0.113.56` — но сработает на любом `203.0.113.*` (та же /24). За корпоративным NAT это работает. **Митигация:** SDK при `Refresh` берёт IP из `X-Forwarded-For` (с проверкой trusted proxies — см. `helpers.go`). Документировать, что consumer должен либо прокидывать XFF, либо явно передавать ClientIP.

### Риск 3 — refresh singleflight не покрывает кросс-инстанс
Если BFF deploys в 2+ replicas, singleflight в одной replica не видит refresh в другой. AUTH может детектить reuse. **Митигация:** в v0.1.0 — accepted, документировать. В v0.2.0+ можно добавить distributed-singleflight через Redis, если станет реальным проблемой.

### Риск 4 — кэш не подхватит мгновенный logout
Юзер делает logout-all на устройстве А → access token устройства Б всё ещё в кэше SDK (до 30s). **Митигация:** документировать, разрешить меньший TTL (down to 5s). Если consumer хочет 0s — `Config.ValidateCacheTTL: 0` отключает кэш полностью (каждый запрос → AUTH).

### Риск 5 — Logger interface заставит consumer писать адаптер даже для silent
**Митигация:** в SDK дефолт — `NoopLogger{}`, ничего настраивать не надо. Consumer пишет адаптер только если хочет логи.

### Риск 6 — integration-тесты требуют AUTH-image
SDK тестируется против реального AUTH. AUTH собирается из исходников локально. CI требует либо собирать AUTH в CI (медленно), либо опубликованный image (требует DevOps работ в auth-репо). **Митигация:** в TASK-001 решить — собираем локально для разработки, в CI integration-тесты делаем опциональными. Если станет проблемой — отдельный devops-REQ на публикацию AUTH image в GHCR.

### Риск 7 — go.mod лишних зависимостей
Если случайно добавить большую liib (например `go.uber.org/fx` через копипаст), consumer потащит. **Митигация:** код-ревью каждого TASK включает `go mod why` для каждой новой зависимости.

# Проактивный мониторинг агентов - Универсальный паттерн

## Проблема

**Текущее (неправильное) поведение:**
```
1. Оркестратор запускает агента в background
2. Вызывает TaskOutput(block=true, timeout=600000)  ← БЛОКИРУЕТСЯ на 10 минут!
3. Если агент зависнет → timeout после 10 минут
4. Нет информации о прогрессе
5. Нет возможности раннего обнаружения проблем
```

**Последствия:**
- ❌ Зависшие агенты обнаруживаются поздно (после timeout)
- ❌ Нет видимости прогресса для пользователя
- ❌ Невозможно оценить оставшееся время
- ❌ Оркестратор простаивает вместо полезной работы

## Решение: Проактивный мониторинг

**Правильное поведение:**
```
1. Запустить агента в background
2. Сохранить agent_id
3. ПЕРИОДИЧЕСКИ проверять статус (каждые 30-60 сек):
   - TaskOutput(agent_id, block=false, timeout=5000)
4. Между проверками делать ПОЛЕЗНУЮ РАБОТУ
5. Показывать прогресс пользователю
6. Обнаруживать зависание (no progress > 5 min)
7. При завершении всех агентов → продолжить workflow
```

**Преимущества:**
- ✅ Раннее обнаружение зависших агентов
- ✅ Видимость прогресса
- ✅ Оркестратор делает полезную работу, не простаивает
- ✅ Пользователь получает feedback
- ✅ Возможность досрочного прерывания проблемных агентов

## Паттерн 1: Мониторинг одного агента

### Использование

Применяется когда запущен **один агент** (refactorer, code-reviewer, debugger, etc).

### Реализация

**Шаг 1: Запустить агента с сохранением ID**

```
🤖 Запускаю агента `{agent_type}` в background...

Task tool:
  subagent_type: "{agent_type}"
  prompt: "{detailed_prompt}"
  run_in_background: true
  description: "{short_description}"

Агент запущен (ID: {agent_id[:7]})
Пока он работает, выполняю подготовительные задачи...
```

**Шаг 2: Определить полезную работу**

Пока агент работает, оркестратор должен делать подготовительные задачи:

| Агент | Полезная работа оркестратора |
|-------|------------------------------|
| `refactorer` | • Обновить tasks_list.yaml<br>• Подготовить validation команды<br>• Проверить git status<br>• Прочитать success criteria из PRP |
| `code-reviewer` | • Анализировать breaking changes<br>• Создать шаблон result report<br>• Собрать git commit info |
| `debugger` | • Подготовить test commands<br>• Проверить dependencies<br>• Создать bug report template |
| `debugger-complex` | • То же что debugger<br>• Подготовить race detector команды<br>• Собрать goroutine dump info |
| `unit-test-writer` | • Обновить mockery config<br>• Сгенерировать моки<br>• Подготовить test runner commands |

**Шаг 3: Цикл мониторинга с полезной работой**

```bash
# Подготовительные задачи (выполнять между проверками)
work_items = [
    "Обновление tasks_list.yaml",
    "Подготовка validation команд",
    "Проверка git статуса",
    "Анализ success criteria из PRP",
]

work_index = 0
check_count = 0
```

**Iteration 1 (t=0s):**
```
📋 Выполняю: Обновление tasks_list.yaml (1/4)
[выполнить обновление tasks_list.yaml]

⏳ Проверка агента {agent_type}...
[TaskOutput(agent_id, block=false, timeout=5000)]

Status: running

[sleep 30]
```

**Iteration 2 (t=30s):**
```

[выполнить подготовку команд]

⏳ Проверка агента {agent_type}...
[TaskOutput(agent_id, block=false, timeout=5000)]

Status: running
Progress: {tokens} tokens, {duration}

Ожидаю 30 секунд...

```

**Iteration 3 (t=60s):**
```

[git status, git diff --stat]

⏳ Проверка агента {agent_type}...
[TaskOutput(agent_id, block=false, timeout=5000)]

```

**Iteration N (агент завершён):**
```

Результат агента:
[показать краткую сводку из output]
```

**Шаг 4: Обработать результат**

```
Агент {agent_type} завершил работу.

Изменённые файлы:
{список файлов из git diff}

Продолжаю выполнение workflow...
```

### Обнаружение зависания

**Критерии зависания:**

1. **No progress > 5 min:**
   - Tokens не растут между проверками
   - Duration увеличивается, но output не меняется

2. **Excessive duration:**
   - Агент работает > 10 минут
   - Превышен ожидаемый максимум для типа агента

3. **Error state:**
   - TaskOutput возвращает status="failed"
   - Output содержит stack trace или error message

**Действия при обнаружении:**

```
⚠️ ОБНАРУЖЕНО ЗАВИСАНИЕ АГЕНТА!

Agent: {agent_type} (ID: {agent_id[:7]})
Status: No progress for {duration}
Last tokens: {tokens} (не изменялись {stuck_duration})
Duration: {total_duration}

Прочитаю последние 100 строк output для диагностики...

[Bash: tail -100 {output_file}]

Анализ:
{показать последние строки output}

Возможные причины:
- Бесконечный цикл в агенте
- Ожидание timeout внешнего ресурса
- Deadlock в concurrency коде

Действия:
1. Если агент точно завис → убить через KillShell({agent_id})
2. Перезапустить с меньшим scope или другими параметрами
3. Если критично → прервать выполнение задачи, сообщить пользователю
```

### Временные интервалы

**Рекомендуемые интервалы проверки:**

| Ситуация | Интервал | Причина |
|----------|----------|---------|
| Есть полезная работа | **30 сек** | Баланс между responsiveness и overhead |
| Вся работа завершена | **60 сек** | Реже проверяем когда только ждём |
| Долгий агент (>5 мин) | **90-120 сек** | Снижаем overhead для длинных операций |
| Агент близок к завершению | **15 сек** | Часто проверяем в конце |

**Не использовать:**
- ❌ < 15 сек - слишком частые проверки, лишние токены
- ❌ > 2 мин - можем пропустить быстрое завершение или зависание

## Паттерн 3: Последовательный запуск с мониторингом

### Использование

Применяется когда задачи **зависимы** и должны выполняться последовательно.

### Реализация

```
Задача разбита на 2 последовательных этапа:
1. refactorer → изменить код
2. code-reviewer → проверить изменения

═══════════════════════════════════════════════════════════
ЭТАП 1: Рефакторинг кода
═══════════════════════════════════════════════════════════

🤖 Запускаю агента `refactorer`...
[запуск с мониторингом по Паттерну 1]

✅ Агент refactorer завершён
Изменено файлов: 5

═══════════════════════════════════════════════════════════
ЭТАП 2: Code Review
═══════════════════════════════════════════════════════════

🤖 Запускаю агента `code-reviewer`...
[запуск с мониторингом по Паттерну 1]

✅ Агент code-reviewer завершён
Замечания: 2 CRITICAL, 5 WARNING, 8 SUGGESTION

Исправляю CRITICAL замечания...
[исправление через debugger]

Все этапы завершены успешно!
```

## Интеграция в CLAUDE.md

**Секция для добавления в CLAUDE.md:**

```markdown
## Проактивный мониторинг агентов (ОБЯЗАТЕЛЬНО)

> **КРИТИЧЕСКИ ВАЖНО:** При запуске агентов в background оркестратор ДОЛЖЕН проактивно мониторить их статус.

### Правила мониторинга

**❌ НЕПРАВИЛЬНО (блокирующее ожидание):**
```
agent_id = Task(run_in_background=true)
TaskOutput(agent_id, block=true, timeout=600000)  # Блокируется на 10 минут!
```

**✅ ПРАВИЛЬНО (проактивный мониторинг):**
```
1. Запустить агента в background
2. Сохранить agent_id
3. Определить полезную работу (обновление tasks_list, подготовка команд)
4. Цикл:
   - Сделать одну работу
   - Проверить статус: TaskOutput(agent_id, block=false, timeout=5000)
   - Показать прогресс
   - Sleep 30-60 сек
   - Повторить пока статус != completed
5. Обработать результат агента
```

### Когда применять

| Сценарий | Паттерн | Интервал |
|----------|---------|----------|
| Один агент | Паттерн 1 | 30 сек (работа) / 60 сек (ожидание) |
| Параллельные агенты | Паттерн 2 | 30 сек, адаптивно |
| Последовательные этапы | Паттерн 3 | 30 сек для каждого этапа |

### Полезная работа по агентам

| Агент | Полезная работа оркестратора |
|-------|------------------------------|
| refactorer | Обновить tasks_list, подготовить validation, проверить git |
| code-reviewer | Анализ breaking changes, создать report template |
| debugger | Подготовить test commands, проверить dependencies |
| unit-test-writer | Обновить mockery config, сгенерировать моки |

**Детальный паттерн:** [.claude/patterns/proactive_agent_monitoring.md](.claude/patterns/proactive_agent_monitoring.md)
```

## Метрики и оценка стоимости

### Overhead мониторинга

**Для одного агента (3 минуты работы):**
```
Проверок: 3 мин / 30 сек = 6 iterations
Вызовов: 6 TaskOutput calls
Токены: 6 × ~500 tokens = 3k tokens
Стоимость: ~$0.015 USD (haiku model)
```

**Для 10 параллельных агентов (3 минуты работы):**
```
Проверок: 3 мин / 30 сек = 6 iterations
Вызовов: 6 × 10 агентов = 60 TaskOutput calls
Токены: 60 × ~500 tokens = 30k tokens
Стоимость: ~$0.15 USD (haiku model)
```

**Вывод:** Мониторинг стоит $0.01-0.20 за сессию, что приемлемо для улучшения UX.

## Обработка ошибок

### При failure агента

```
❌ Агент {agent_type} завершился с ошибкой!

Error: {error_message}

Читаю последние 50 строк output для диагностики...
[Read или tail -50 {output_file}]

Диагностика:
{анализ ошибки}

Действия:
1. Если recoverable error → перезапустить агента с уточнениями
2. Если configuration error → исправить промпт и перезапустить
3. Если critical failure → прервать workflow, сообщить пользователю
```

### При зависании

```
⚠️ Агент {agent_type} зависнул!
No progress for {duration}

Читаю последние 100 строк output...
[tail -100 {output_file}]

Последняя активность:
{показать последние строки}

Решение:
1. Убить агента: KillShell({agent_id})
2. Перезапустить с меньшим scope
   Например: вместо всего lib/core → только lib/core/config
```

## FAQ

**Q: Что если агент завершится между проверками?**

A: Система отправляет notification о завершении, оркестратор получит его сразу. Периодические проверки — это дополнительная страховка для случаев, когда notifications задерживаются.

**Q: Сколько стоит мониторинг?**

A: Для 10 агентов за 3 минуты: ~60 TaskOutput calls × 500 tokens = 30k tokens ≈ $0.15 USD (haiku). Это приемлемо для улучшения UX.

**Q: Можно ли использовать более длинные интервалы?**

A: Можно, но:
- < 30 сек - лишние токены
- > 2 мин - поздно обнаружим зависание, плохой UX

Оптимум: 30-60 сек.

**Q: Как мониторить bash-command-runner?**

A: bash-command-runner обычно запускается синхронно (НЕ в background), так как команды выполняются быстро. Если запускается в background для долгих команд, применять тот же паттерн.

**Q: Что делать если нет полезной работы?**

A: Всегда есть что делать:
- Обновить tasks_list.yaml
- Проверить git status
- Подготовить следующие команды
- Прочитать requirements из PRP/TASK файлов
- Создать шаблоны отчётов

Если действительно ничего нет - просто проверять статус каждые 60 сек и показывать progress bar.
